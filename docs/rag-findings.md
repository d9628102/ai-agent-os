# PSF EIM RAG 問答:實測結果與已知限制

記錄 `scripts/rag_answer.py` 在 GX10 上針對 `psf_eim_kb` 的實測結果。
測試集為 `scripts/data/psf-eim-qa-questions.txt`(5 題內容問題 + 1 題
負向對照)。

> **樣本數警告**:以下每種設定都只跑過**一次**。趨勢明確的項目(例如
> 耗時差異達 4.8 倍)可以採信,但涉及回答品質的細微差異(例如越界抑制
> 效果)在單次測試下**不足以下定論**,待補測見文末。

## 思考模式開關的 A/B 對比

同一組 6 題,思考模式開啟／關閉的差異:

| 問題 | 思考開啟 | 思考關閉 | 加速 |
|---|---|---|---|
| 五大產品矩陣 | 19.21s | 4.56s | 4.2× |
| Decision Matrix 核心模組 | 14.54s | 2.60s | 5.6× |
| 跟 ERP/CRM 的差異 | 31.12s | 9.44s | 3.3× |
| 負責客戶服務的 Agent | 17.19s | 1.56s | 11.0× |
| 架構分成幾層 | 15.10s | 3.20s | 4.7× |
| 定價(負向對照) | 14.65s | 1.89s | 7.8× |
| **平均端到端** | **18.63s** | **3.87s** | **4.8×** |

輸出 tokens 從 2379 降到 446 —— **約 81% 的生成量是使用者看不到的推理
內容**。tokens/s 兩者都在 16–22 之間,幾乎沒變,所以加速完全來自產出量
減少,不是吞吐提升。

耗時結構:**生成佔 99.8%**。embedding 約 0.03–0.05 秒、Qdrant 檢索約
0.00–0.01 秒,兩者相對於生成可以視為免費。要再壓低延遲只有從生成端下手。

## 正確性

兩種設定下,**5 題內容問題的事實全部正確**,沒有捏造任何 PSF 產品、模組
或 Agent 名稱。

**負向對照(定價)在兩種設定下都守住了** —— 都明確回答「文件中未提及」,
沒有編造價格。防幻覺的保護**不依賴思考模式**。

## Known Issue #7:`--think` vs `--no-think` 對回答品質與速度的取捨(待補測)

> 編號說明:此編號屬於本文件(RAG 行為)的獨立序列,與
> `docs/gx10-known-issues.md` 的 #1–#7(環境建置問題)是不同的兩套編號。
> 那份文件的 #7 是 HF_TOKEN 非 ASCII 字元的問題。

**現象**

關閉思考模式(`--no-think`)平均可帶來 4.8× 生成加速(18.63s → 3.87s),
且事實正確性、防幻覺(負向對照題)皆未退步。但單次測試觀察到,關閉思考
模式後:

- 可能遺漏「命名易混淆」情境下的辨析(例如 Q4:Service Matrix 的 Core
  Module「Customer Success」與 Agent Matrix 底下的「PSF Customer Success
  Agent™」,兩者是否為同一實體,思考開啟版本會主動釐清,關閉版本未辨析)
- 可能遺漏列舉型問題的完整組成細節(例如 Q5:四層架構名稱,思考關閉版本
  只列層名,思考開啟版本會列出各層組成元件)
- 偶爾出現文件中未提供譯名的自行補充翻譯(程度輕微,屬翻譯而非事實捏造)

**原因**

思考模式(reasoning)讓模型有機會在生成最終答案前,先對照文件內容做一輪
消歧義與完整性檢查;關閉後省去這個步驟,直接輸出結論,速度大幅提升但
可能跳過需要「多想一步」才能發現的細節。

**目前狀態:已完成重複測試,差異確認為穩定,非抽樣雜訊**

2026-09-07 以 `scripts/run_think_ab_test.py` 完成重複測試:固定新 system
prompt,Q3/Q4 兩題 × 思考開啟／關閉 × 各 3 次獨立子行程 = 12 次生成。
逐次判讀結果(原始逐次回答見
[`docs/think-mode-ab-test-results.md`](think-mode-ab-test-results.md)):

| 題目 | 模式 | 第1次 | 第2次 | 第3次 | 出現機率 |
|---|---|---|---|---|---|
| Q3 越界 | think 開啟 | 無 | 無 | 無 | **0/3** |
| Q3 越界 | think 關閉 | 有 | 有 | 有 | **3/3** |
| Q4 辨析保留 | think 開啟 | 有 | 有 | 有 | **3/3** |
| Q4 辨析保留 | think 關閉 | 無 | 無 | 無 | **0/3** |

兩個指標都是 **0/3 對 3/3 的極端分離**,沒有 2/3 vs 1/3 這種模糊比例,
因此可判定為**穩定的系統性差異**,不是單次抽樣運氣。耗時同樣穩定:
思考開啟 41.3/42.0/40.7 秒,關閉 10.4/10.4/10.1 秒(每次含 2 題),
組內變異都在 1.5 秒內,**4.0× 的速度差同樣穩定**。

**混淆變因已排除**:本次兩組都使用**同一份**加嚴後的 system prompt,
唯一變數是思考模式。結果顯示加嚴的 prompt **單獨不足以**防止越界
(思考關閉時仍 3/3 發生),真正發揮作用的是思考模式本身。

**重要的認知修正:Q3 其實是第二題負向對照,而先前沒有意識到**

文件只寫了「PSF EIM 並不是 ERP、CRM」,**從未說明 ERP/CRM 是什麼、
做什麼**。因此嚴格有依據的回答應該是「文件不足以支撐這個比較」。

- **思考開啟 3/3 正是這樣回答**:「文件中未提及足夠資訊以說明兩者差異」,
  明確拒絕比較,並說明文件只講了我方定位。
- **思考關閉 0/3**:每一次都「生出」一個比較,用世界知識補上文件的空白
  (「ERP 和 CRM 通常聚焦於企業資源規劃與客戶關係管理」等)。

這修正了先前記錄的「關閉思考時事實正確性與防幻覺皆未退步」——**在這類
文件無法支撐的問題上,關閉思考確實會讓 grounding 退步**。它沒有捏造 PSF
自身的事實,但會(a)對第三方做出無來源的斷言,(b)不告訴使用者「文件其實
回答不了這個問題」。第 (b) 點比第 (a) 點更值得注意:使用者會拿到一個看起來
完整、有結構、實則部分無來源的答案,而且沒有任何警訊。

**決定:選項 1 與選項 2 併行,兩條線各自完成後合併**

動態切換(選項 2)當時被列為「長期方向」,判斷需要額外實作與誤判率
驗證、不該卡住 Phase 1 其他工作。與此同時,另一條並行的工作線
(rule-based `detect_think_reason()`)已經把選項 2 做出來並在 GX10 上
端到端驗證過——兩邊是在同一份 base 上獨立進行的,直到 merge 這份文件
時才發現彼此的存在。合併後的結論是**兩個選項都保留,疊在一起用**:
`DEFAULT_THINKING`(選項 1)當保底,`detect_think_reason()`(選項 2)
在有把握時覆寫成開啟。

目前程式碼狀態:
- `scripts/rag_answer.py` 的 `DEFAULT_THINKING = True`(選項 1,對應上面
  Q3/Q4 重複測試的結論)
- 沒有明確加 `--think`/`--no-think` 時,每一題會先跑
  `detect_think_reason()`(選項 2):問題含比較性詞彙(不同/差異/區別/
  比較/差別/對比/相比/相較)或偵測到兩個以上專有名詞(連續大寫開頭英文
  詞,緊鄰詞視為同一實體)就強制開啟思考;其餘情況落回 `DEFAULT_THINKING`
- 明確傳入 `--think` 或 `--no-think` 時,一律照使用者說的做,
  `detect_think_reason()` 不會覆寫明確指定的選擇

> **旗標政策**:這個預設值已經改過三次,因此 `--think` 與 `--no-think`
> **兩個旗標永久並存**,預設值獨立成 `DEFAULT_THINKING` 常數。日後調整
> 政策只需改那個常數,**不會讓任何人既有的指令失效**。同時給兩個旗標會
> 明確報錯(argparse 互斥組)。
>
> 連帶修正:`scripts/run_think_ab_test.py` 原本靠「不加旗標 = 思考關閉」
> 來跑對照組。預設翻轉後這會讓**兩臂都在思考開啟下執行**,A/B 實際上
> 什麼都沒比較,卻仍產出看似正常的結果。現已改為兩臂都**顯式**帶旗標。

**優先順序已實測驗證:明確旗標一律蓋過 `detect_think_reason()`**

曾經懷疑「`--no-think` 加了之後,規則偵測到高風險題型(比較句/命名混淆)

## 結構化判斷 prompt 設計永久檢查清單：「答案忠實≠沒問題」混淆家族

> 這一節跟上面「Known Issue」系列是不同性質的記錄——不是某一次實測的
> 發現，是**跨多個功能重複出現三次**的同一類 prompt 設計錯誤，記錄下來
> 是為了讓之後新增任何結構化判斷 prompt（紅旗/評分/veto/未來任何新的
> LLM 分類判斷任務）時，動手寫 prompt 之前**主動**核對這份清單，不要
> 每次都等事後測試才抓到——跟 `test_generation_agent.py` 的 `SYSTEM_PROMPT`
> 永久加上「think 標籤要配對」規則同一個處理原則。

**這個混淆家族目前抓到三次**，都是同一個根本原因：每次寫一個新的結構化
判斷 prompt 時，容易只顧著這次判斷的具體規則內容，忘記把之前已經驗證
過的通用防呆原則一起複製過去——即使表面上是「新任務」，底層的判斷
陷阱是同一個。

1. **紅旗判斷（`red_flag_detection.py`）：「答案忠實≠沒有紅旗」**。
   最早發現：模型把「判斷是否構成紅旗」跟「查核系統回答有沒有忠實引用
   文件」搞混，只要回答忠實轉述文件內容就判定沒有紅旗，即使轉述的內容
   本身描述了一個矛盾情境。修正方式：明確聲明「這不是在查核回答有沒有
   忠實引用」，即使回答完全忠實、每個主張都有依據，回答描述的『情境
   本身』仍可能構成紅旗。
2. **評分（`scoring.py`）：「無紅旗≠無負面訊號」**。同一個混淆家族的
   變體：模型把「這題沒有被標記成紅旗」誤解成「答案內容沒有負面事實」，
   即使答案裡明確寫了負面事實（例如「3年內更名3次」），只要沒有矛盾
   結構、沒被紅旗判斷器標記，評分就偏向給高分。修正方式：明確區分
   「沒有偵測到矛盾結構」跟「內容正面、應給高分」是兩件不同的事。
3. **veto 判斷（`veto_check.py`，這一輪同一個 session 裡連續踩到兩次**
   同一家族的不同子案例）：
   - 子案例一：跟第 1 點**完全一樣的錯誤**，只是換了個新任務（矛盾型
     veto 判斷）就忘記在新 prompt 裡包含那段澄清——模型一開始把「這題
     的回答有沒有忠實引用檢索片段」當成判斷依據，只要回答忠實、每個
     主張都有片段支持，就判定不觸發，即使回答轉述的『簡報宣稱 vs 財報
     事實』本身就是矛盾。
   - 子案例二（**這是這個家族目前最細的一個變體，值得特別記錄**）：
     修正子案例一之後，模型又卡在veto規則的**字面定義文字**——「資源
     不實」的文件定義寫的是「只說有資源，但不能驗證」，模型因此推理
     「這裡財報有具體數字可以查核，代表不是『不能驗證』，所以不算資源
     不實」，反而因為查到了明確反證，變成「排除觸發」的理由，完全
     顛倒。修正方式：明確提醒「查到反證」比「查不到依據」是**更強、
     更明確**的觸發情況，不是例外，不要因為查核資料寫得很具體、很有
     數字，就反過來認為「這樣就不算」。

### 之後新增任何結構化判斷 prompt，動手前主動核對三項

1. **忠實≠沒問題聲明**：明確聲明「這不是在查核回答有沒有忠實引用/
   查核到依據」——即使回答完全忠實、每個主張都有片段依據，回答描述的
   『情境本身』仍可能構成這次要判斷的目標（矛盾/缺失/風險/其他任何
   分類）。不能假設模型會自己想到這一層，每個新的判斷任務都要重新寫
   這句話，不能只靠「之前別的 prompt 有寫過」。
2. **反證優先於缺乏依據**：如果這次的判斷邏輯屬於「矛盾型」（找『主張
   跟查核結果對不上』），要明確提醒模型「查到明確反證」是比「查不到
   依據/無法驗證」更強的觸發訊號，不是例外或反而排除的理由。
3. **規則名稱/定義文字的字面語感可能誤導判斷模式**：如果規則或類別的
   名稱、定義文字用的字眼（例如「不能驗證」「不明」「不清」）在語感上
   偏向另一種判斷模式（缺失型 vs 矛盾型），要在 prompt 裡明確覆寫這種
   字面語感造成的誤導，不要讓模型自己去解讀規則名稱字面意思、因而卡在
   跟實際判斷邏輯不一致的推理路徑上。

診斷方法沿用既有慣例：**逐句看 `<think>` 推理過程定位根因，不是碰運氣
重跑**——veto_check.py 這兩次都是靠直接印出模型的 thinking 內容才抓到
具體卡在哪一句推理，不是先猜測再驗證。

### 生成一直失敗但原因不明時的標準診斷做法：對照組實驗 + 量測回應欄位

上面那條（讀 thinking）處理的是「模型判斷錯了，但為什麼」。另一類問題是
「生成本身一直失敗，連原因都不明」——這種時候**不要靠改 prompt 試運氣**，
用下面這套做法，實際用它定位過測試生成代理連續五次失敗的原因：

1. **先量測回應欄位，不要只看最終錯誤訊息。** 把完整回應存下來看
   `finish_reason`、`usage.completion_tokens`、輸出長度、以及輸出「結束在
   哪個位置」。實際案例：外層報的是 `invalid character '，'` 語法錯誤，
   看起來像模型寫壞程式碼，但回應欄位顯示 `finish_reason='stop'`、只用了
   843 tokens、字串常值在中途沒收尾——真正的問題是生成提早結束，語法錯誤
   只是下游症狀。**外層錯誤訊息指向的地方經常不是根因。**
2. **設計對照組，一次只變一個條件。** 三組請求其他條件完全相同，只改
   「要求輸出的內容有沒有字面的特殊標記」：(A) 要求輸出含字面標籤、
   (B) 同樣內容但標籤用字串相加組出來、(C) 完全無關標籤的對照組。結果
   A 完整結束但模型**自己把標籤換成別的字**（`<think>` → `<x>`）、B 跟 C
   都正常完成——這才確定機制是「這些標記在對話模板裡是特殊標記」，不是
   prompt 不夠清楚、也不是 max_tokens 不夠。
3. **確認修正沒有把正常路徑弄壞。** 改完工具之後，拿一個跟這次問題無關的
   普通目標跑一次，確認一般情況還是正常（實際做過：改完剝殼邏輯後拿
   `rag_common.py:source_filter` 跑一次，確認草稿正常產出）。
4. **結論要能解釋全部觀察到的現象，不能只解釋一部分。** 中途有兩次以為
   找到原因（先猜 max_tokens 不足、再猜結尾標籤位置的字串樣式），都因為
   「解釋不了其中一組觀察」而被推翻。推翻自己的假設比硬湊一個解釋便宜。

## 觀察但未定位根因的線索：`--style-reference` 檔案較大時的空生成

> 這一節記的是**還沒追到根因、刻意選擇先繞過**的觀察，跟上面兩節（已經
> 追到底的混淆家族、已經定型的診斷方法）性質不同——寫下來是為了下次
> 撞到同樣症狀時不用從頭重新診斷，不是宣稱問題已經解決。

**現象**：`test_generation_agent.py` 用 `tests/test_report_helpers.py`
（當時 31 條測試、12KB）當 `--style-reference` 生成
`render_red_flags_section`/`render_consistency_section` 的測試草稿時，
`finish_reason='stop'`（不是 `length`）但只生成 2 個 token（`<think>`
就停），完全沒有內容。重複同一請求 3 次，2/3 次重現這個症狀；分別單獨測
兩個目標函式（拆開測，不是因為合在一起才發生），兩個都各自重現；換成
較小的 `tests/test_scoring.py`（9.4KB）當風格基準，其他條件完全不變，
問題消失、正常生成 1852 token。

**根因未定位，程度到「強相關」為止**：只做了「換一個較小的風格基準檔」
這一個對照，還沒確認是純粹的檔案長度效應、還是 `test_report_helpers.py`
裡某段特定內容觸發（例如裡面同時出現多種 emoji 常數跟大量參數化案例），
也還沒測試「同樣長度但內容不同的檔案」這種能真正切開「長度」跟「內容」
兩個變因的對照組。刻意沒有繼續深挖——追這條線需要再跑好幾組對照實驗，
這一輪的目標是把測試批次做完，不是把這個環節研究透。

**目前的繞過方式**：這批（render_red_flags_section/render_consistency_
section）改用 `tests/test_scoring.py` 當風格基準，生成正常。

**之後遇到同樣症狀時的處理節奏**：不用重新從頭診斷，先直接換一個較小的
風格基準檔（例如 `tests/test_scoring.py`、`tests/test_veto_check.py` 這種
不到 10KB 的檔案）試繞過。如果換檔案後同一批又發生第 2 次，才值得認真
分配資源做真正的對照實驗深挖根因——這跟 veto 判斷那個「答案忠實≠沒問題」
混淆家族連續踩到第四次才真正下決心做完整診斷是同一個節奏：**用出現頻率
決定要不要投入資源追根究柢，不是每次撞到就立刻挖到底**。

**後續更新（下一批測試補齊時的實際觀察）**：換小檔案這個繞過方式**沒有
穩定重現**——同一批（`render_scoring_section`/`render_veto_section`）換了
同樣的小檔案，仍然連續失敗 3 次。另外用受控實驗排除了「`±` 這個特殊
Unicode 字元」的假設（同一份函式原始碼含 `±` 跟不含 `±` 的版本都各自
成功生成過）。目前唯一乾淨的訊號是：**兩個目標函式合併成一次生成請求時
的失敗率，明顯高於各自單獨生成**——沒有繼續深挖這一點的機制（一次只變
一個條件的對照組還沒做完就先止損），改用「每次只生成一個目標函式、事後
自己合併草稿」繞過，這一輪都成功了。結論仍然停在「機率性、跟 prompt
複雜度/長度有某種關聯，但沒有找到單一決定性因子」，跟第一次記錄時一樣
誠實：**這是繞過症狀，不是解決問題**。

## 假陽性測試模式圖鑑：草稿「測試通過但沒測到東西」的四種形態

> 這份圖鑑取代原本的「草稿不能自己重新定義模組層級常數/helper」那條
> 單一檢查清單——批次補測試（A～G）跑下來，「通過但沒測到東西」不是
> 單一模式，累積到第四種時已經看得出至少兩種不同成因，值得拆開整理成
> 圖鑑，而不是繼續塞進同一條清單底下。**這種錯誤比明顯的測試失敗更
> 危險**：失敗的測試會被人工審核時發現並修正，通過但沒測到東西的測試
> 會被誤以為已經有防線，之後真正的邏輯壞掉也不會被抓到。
>
> 前三種形態的共同點：**斷言本身沒錯，但它斷言的對象沒有真正經過目標
> 邏輯**——原因分別是 mock 資料形狀不對、抄錄了錯誤的替代定義、或斷言
> 寫成了不管什麼輸入都會成立的樣子。第四種形態不一樣：**斷言的對象確實
> 經過了目標邏輯，但另一個條件搶先決定了結果，該測試真正想驗證的那個
> 判斷分支從來沒被走到**——是兩個條件耦合造成的隱蔽假陽性，比前三種更
> 難察覺，因為連「這個測試在測哪個分支」這個問題，不逐行對照原始碼的
> if/elif 順序是看不出來的。

### 形態一：mock 資料形狀錯了，目標分支沒被執行到

**案例（批次A）**：`test_render_consistency_section_consistent`
（`generate_report.py` 測試補齊）。mock 的 entry 把 `source` 欄位放錯
位置（塞進 `extraction` 裡面，不是 entry 自己的欄位），導致真正的函式
讀不到 `source`，「涵蓋文件」那個分支從未被執行到，但斷言沒有要求驗證
這個分支，測試照樣「通過」。

**成因**：mock 資料的欄位結構跟目標函式實際讀取的路徑不一致，通常是
憑印象猜結構、沒有對照真正的呼叫端程式碼逐欄核對。

**審核動作**：mock 一個 entry/dict 之前，找到目標函式裡讀這個欄位的
那一行（`entry["x"]`／`entry.get("x")`），確認 mock 的巢狀層級跟那一行
完全一致，不要憑函式名稱或參數名稱猜測結構。

### 形態二：草稿自己重新定義了目標函式依賴的模組層級常數/helper

**案例（批次C）**：`test_read_valid_override_token_not_found`／
`test_read_valid_override_token_expired`（`code_review_agent.py` 測試
補齊）。草稿**自己重新定義了一個同名的 `override_log_path()` helper**，
回傳跟真正函式不同的檔名（`override_log.jsonl` vs 真正的
`.code_review_overrides.jsonl`）。`read_valid_override()` 內部用真正
路徑找檔案，永遠找不到 mock 寫的檔案，永遠回傳 `None`——兩條測試斷言
`result is None`，剛好「通過」，但通過的原因是「檔案根本沒被讀到」，跟
「token 真的比對出不符合／過期」這個測試名稱聲稱要驗證的邏輯完全無關。
這次踩在這輪特別高風險的一對函式上（override/SHA range 比對邏輯，這個
專案已經真實發生過一次相關事故），程度比形態一更嚴重。

**成因**：目標函式依賴某個模組層級的常數或 helper 函式，草稿生成測試
資料/mock 時，沒有直接 import 真正的定義去對齊，而是自己憑印象重寫一份
「看起來應該差不多」的版本，兩者一旦有任何落差，測試就會在跟真正邏輯
脫節的假資料上運行。

**審核動作**：看到草稿裡出現跟目標函式同一個模組裡已有名稱相同或功能
相似的自訂函式/常數定義，直接視為可疑，逐一核對是不是應該改成
`import` 真正的定義，而不是自己重寫一份。

### 形態三：斷言寫成恆真（不管實際值是什麼都會成立）

**案例（批次E）**：`assert expected_body in result`，其中
`expected_body = ""`。空字串是任何字串的子字串，這條斷言不管 `result`
實際內容是什麼都會成立，等於完全沒有驗證「這個區塊的內容應該是空的」
這件事。

**成因**：用「子字串包含」這種寬鬆斷言處理「預期輸出是空/沒有這一段」
的情境時，沒有意識到空字串是這種寬鬆斷言的退化情況——`x in y` 對任何
`y` 在 `x=""` 時永遠是 `True`，跟真正驗證「這裡沒有內容」的斷言方式
（例如 `expected_body not in result` 反過來驗證、或直接斷言完整區塊的
確切內容）完全不同。

**審核動作**：看到 `assert <變數> in <結果>` 這種子字串斷言，先確認
`<變數>` 不會是空字串；如果情境本來就是要驗證「這裡沒有這段內容」，
斷言方向要反過來寫（`not in`）或改成比對完整、確切的字串內容，不要用
「包含一個空字串」去頂替。

### 形態四（新型態，跟前三種成因不同）：兩個條件同時成立，其中一個從未被單獨測到

**案例（批次F）**：`check_deterministic()` 的
`test_check_deterministic_empty_answer`——測試用的 `completion_tokens`
剛好等於門檻值（撞到 `max_tokens - 8`），所以不管「答案是不是空白」這個
條件本身判斷得對不對，`not_truncated` 都會是 `False`。變異測試把「空白
答案判斷」整段邏輯刪掉，這條測試依然通過——因為它從頭到尾都是靠另一個
無關的條件（撞到 token 上限）在撐著，不是靠它宣稱要測的那個條件。

同一批次的 `build_dimension_bundle()` 也有一個相同機制的案例：
`test_build_dimension_bundle_no_conflict` 給的 `status: "ok"` 在真實
系統裡根本不存在（真實值只有 `consistent`/`insufficient`/`conflict`），
而且 `entries` 是空的——題目在還沒輪到 `status` 檢查之前，就已經被「這個
問題不在衝突組的 entries 裡」這一關擋掉了。刪掉 `status` 過濾邏輯，這條
測試一樣通過。

**成因跟形態一～三不同**：這裡的斷言本身沒錯、mock 資料形狀也對、目標
函式也真的被呼叫到了——問題是**測試案例的兩個輸入條件耦合在一起**，
其中一個條件（例如 token 數已經超標、或資料根本不符合進入該分支的
前提）搶先決定了輸出，另一個條件（測試名稱宣稱要驗證的那個）事實上
從來沒有被單獨檢驗過。這種假陽性藏得比前三種更深：草稿的斷言、mock
形狀、import 全部正確，唯一的問題是「選錯了測試輸入的組合」，不逐行
對照目標函式內部的分支順序（哪個條件先判斷、先決定結果）看不出來。

**審核動作**：目標函式裡如果有多個條件共同決定同一個輸出（`A and B`、
連續的 `if`/`elif` 判斷鏈、或某個分支的前提本身就排除了其他條件的影響
範圍），每個條件都要有一條測試把**其他條件固定在「不會搶先決定結果」
的安全值**、只變動自己要測的那個條件。具體檢查動作：對每一條斷言，
問「如果把這條測試宣稱要測的那個判斷邏輯整段刪掉或改壞，這條測試會不會
真的失敗」——回答不出來、或需要驗算才知道，就要重新設計測試輸入，而不
是只看斷言字面上有沒有針對正確的欄位。這個問題比前三種更需要用**變異
測試**才能穩定抓到，光靠人工審閱斷言字面很容易漏看。

---

**四種形態的共同結論**：「一次生成就全部通過」永遠不是核准的理由，
每一條斷言都要能回答「如果目標邏輯壞掉，這條測試真的會失敗嗎」——形態
一～三靠仔細核對斷言跟 mock 就能回答，形態四通常要靠變異測試才能穩定
驗證,靠人工審閱斷言字面容易漏看。

### 圖鑑補充：行銷文案任務（任務一）裡我自己引入的四個問題

這四個不是測試生成代理的草稿問題，是我自己寫程式/寫測試/做診斷時引入的。
列在這裡，是因為其中兩個正好是「看起來有防線、其實沒有」的同一家族。

1. **測試資料照著錯誤的診斷寫，測試通過只證明假設自洽（跟形態四同源）**。
   說服力評分解析失敗，我讀輸出尾端時看成「模型把同一份 JSON 輸出兩次」，
   照這個假設寫了修正跟測試（兩份一模一樣的 JSON），測試全過。重跑真實輸入
   還是失敗——實際上第一份少了一個結尾 `}`，第二份才是完整的。測試資料是從
   錯誤的假設複製出來的，所以它只能證明修正跟假設一致，證明不了修正跟真實
   失敗一致。**審核動作**：修一個「真實輸入觸發的失敗」時，修完一定要拿
   那個真實輸入重跑一次；合成測試只能補在後面，不能取代。

2. **守門規則被另一個條件搶先放行（形態四的守門版）**。第一版數字守門
   （Guard B）檢查「數字有沒有出現在來源片段裡」，但 `build_context()` 幫
   每個片段加了「[文件片段 1]」～「[文件片段 8]」標籤，1～8 永遠「出現在來源
   裡」，捏造的個位數會直接過關；同時用子字串比對，「70」會被「1970」蓋過。
   用多位數寫的測試全過，完全看不出漏洞，是重讀自己的程式碼才發現的。
   **審核動作**：比對「X 有沒有出現在 Y 裡」的守門規則，要先確認 Y 裡有沒有
   不屬於真正內容的東西（編號、標籤、格式字元），以及比對是整詞還是子字串。

3. **測試資料違反函式自己的文件化限制（兩次）**。引文比對刻意只抓兩個字
   以上的引號內容，我的測試卻用單字「乙」；另一次把會被剝掉的片段標籤
   寫進測試引文。兩次都是測試失敗、不是假陽性，但教訓一樣：**新測試失敗時，
   先拿測試資料對照函式 docstring 寫明的限制，再決定是改程式還是改測試**。

4. **變異測試「沒訊號」要先分類，再決定怎麼處理**。加了 code fence 解析路徑
   之後，拿掉原本「從第一個 `{` 解析」那段的變異沒有任何測試失敗。這跟任務三
   M1 的「沒訊號」不同：M1 是等價變異（改了寫法，但對任何輸入的值都一樣），
   誠實記錄即可；這次拿掉的程式碼對「JSON 後面接一段說明文字、沒有 fence」
   這種真實可能的輸出有作用，是真正的測試缺口，所以補了測試。**判斷方式**：
   問「有沒有任何輸入會因為這段程式碼被拿掉而得到不同結果」——有，就是缺口。

## 測試生成代理的知識缺口：從「操作習慣提醒」升級成「工具自動化」

> 跟上面四種假陽性形態不同性質——不是斷言邏輯錯、不是機率性生成失敗，
> 是**模型沒有依據可以對**：目標函式的參數是某個外部設定檔（例如
> `scripts/data/scoring_templates.json`）的資料結構時，模型看不到那份
> 檔案的真實內容，每次都會自己編一個看起來合理但跟真實 schema 不相容
> 的假結構。

**已發生三次，同一種錯法**：
1. 生成 `compute_scoring_summary()`/`build_scoring_banner_line()` 的測試
   草稿時，虛構一套百分制模板（權重加總125、用 `grades` 不是
   `grade_bands`、缺 `max_score_per_dimension`）。
2. 生成 `render_scoring_section()` 的測試草稿時，虛構的模板缺
   `grade_bands` 這個必填 key。
3. 生成 `load_scoring_template()`（批次F）的測試草稿時，憑空在真實檔案
   結構外面多加了一層 `{"templates": {...}}` 包裝——真實檔案最上層直接
   就是模板名稱，沒有這層包裝。

**第一、二次發生後的處理決定：不改動工具本身，改成操作習慣**——之後
下 `--hint` 時人工把真實 JSON 內容直接貼進去。**這次（第三次）證明這個
決定不夠：光靠「下次記得」不可靠，操作習慣層級的提醒會被同一個人在
不同批次裡重複忘記**——批次F規劃 hint 時判斷「剩下的批次不會再碰到這個
模式」，判斷錯了，`load_scoring_template()` 讀的正好就是這個檔案。

**修正後的處理方式：把偵測跟附加真實內容做成 `test_generation_agent.py`
工具本身的行為，不再依賴人記得**。實作了
`find_referenced_config_files()`：掃描目標函式原始碼（含 docstring，因為
`load_scoring_template()` 本身不寫死路徑，是靠 docstring 講清楚讀哪個
檔案）裡看起來像設定檔路徑的字串（結尾是 `.json`/`.yaml`/`.yml` 的相對
路徑），解析成 repo 內真的存在的檔案，自動讀取真實內容附加進生成請求，
明確標註「不是虛構範例，不能自己發明不相容的結構」。驗證方式：分別對
會命中（`load_scoring_template()`，偵測到
`scripts/data/scoring_templates.json` 並正確附加真實內容）跟不會命中
（`check_deterministic()`、`build_dimension_bundle()`，正確回傳空清單）
兩種情況實際跑過，確認偵測邏輯不是「寫完就假設有效」。

**這條教訓本身也值得記錄**：同一類知識缺口，如果處理方式停留在「人工
記得在 --hint 裡貼」這個層級，重複發生的機率不會隨時間下降——操作習慣
層級的提醒沒有強制力，只有工具本身的行為才靠得住。之後任何類似的「模型
需要看到某份外部檔案真實內容才能正確生成」的情境，第一個該考慮的選項
是能不能做成自動偵測，而不是先寫進操作守則。
## 行銷文案忠實度檢查：守門規則的由來與已知缺口

`scripts/marketing_faithfulness.py` 的判斷分兩層：模型先逐句分類（fact／
rhetoric）並判斷依據，接著一組機械守門規則（A～E、整行漏檢比對）專門擋
模型判得太寬的方向。守門規則每一條都是實測漏抓逼出來的，不是事先設計的：
最高級標題被歸成修辭、捏造的數字整句放行、模型捏造引文當依據、prompt 明文
要求「不能漏句」還是整行漏掉標題。跟孤立 think 標籤同一個教訓——prompt 規則
對模型的約束不到 100%，要擋的東西要用機械方式擋。

**兩級警示**：紅＝無依據（來源找不到支撐、守門規則判定捏造、整行漏檢、查核
失敗、跳過檢查）；黃＝依據無法自動核實（模型拿文案自己的措辭當依據，循環
引用）。兩級都讓 HTML 出現頁首橫幅、行內標記，並以結束碼 3 離開；分兩級是
因為實測循環引用的誤報比真正捏造多，長得一樣的話，看久了會連紅色也習慣性
略過。

**語氣評分綁定事實檢查**：試跑時數字全部捏造的文案拿到 19/20，高於只用
真實事實、刻意寫好的文案（16/20）——評分器照設計不管真假，會獎勵捏造的
具體性。所以忠實度有任何紅/黃、檢查失敗或被跳過時，程式根本不呼叫語氣
評分器，只顯示「因事實檢查未通過，語氣評分不具參考性」。這是工具行為，不是
操作提醒。語氣評分的準確度**尚未驗證**：目前只有一組我自己寫的好/平淡對照，
正式驗證需要 5～10 組人工判斷過的對照文案。

**已知缺口（照實記錄，目前沒有解法）**：

1. 願景/能力被寫成現況：來源只有願景句「建立全球企業智慧的新基礎建設」，
   文案寫「正協助全球企業建立…」，三次都判有依據；來源寫「可以每天完成
   數萬個決策」（能力），文案寫成「每日決策處理量」（實測數據）也會過。
   專門加的 prompt 規則沒有效果，字面守門也擋不到。
2. 軟性效果主張判得偏寬：「即時分析」「決策即時精準」這類來源沒有的效果
   描述，只要句子裡的模組名稱有依據就容易整句放行。
3. 守門規則本身的誤報：描述讀者痛點的「最迫切的課題」被最高級規則攔下；
   「7 核心模組」數量正確但來源沒有寫成數字；循環引用（標黃）裡多數主張
   其實有依據。
4. 同一份文案重跑，被標出的項目會不同（temperature 0 仍有波動）。
5. 結束碼 0 只代表「檢查器沒找到問題」，不是「保證沒有捏造」。
